## تجربهٔ استریم عالی

</div>

<DocsCollapsible title="تجربهٔ استریم عالی">

ساخت رابط چت زمانی ساده بود. یک لیست معکوس با ورودی می‌ساختید. پیام می‌نوشتید، پایین اضافه می‌شد. وقتی جواب می‌آمد، لیست رشد می‌کرد و اسکرول می‌شد. تمام.

استریم آن مدل را می‌شکند. پیام‌ها تکه‌تکه می‌رسند در حالی که شاید هنوز در حال خواندن، اسکرول یا نگاه به جای دیگری باشید.

حالا چالش حفظ جای خواننده است در حالی که گفتگو مدام عوض می‌شود. اگر اشتباه کنید تجربه پرش‌دار می‌شود: افراد به پایین کشیده می‌شوند، زمینه را از دست می‌دهند و باید راه برگشت را پیدا کنند.

در عمل همه چیز به اسکرول برمی‌گردد: کی دنبال کند، کی نگه دارد و کی به خواننده تصمیم بدهد. یک چت استریم عالی باید:

1. **فقط وقتی حرکت کند که خواننده خواسته باشد.** اگر کسی می‌خواند، او را جابه‌جا نکنید. اسکرول خودکار هرگز نباید پیش‌فرض باشد.
2. **فقط تا وقتی دنبال می‌کنند، دنبال کنید.** اگر روی لبهٔ زنده هستند، استریم را در دید نگه دارید. اگر دور شدند، همان‌جا رهایشان کنید.
3. **هر تعامل یک سیگنال است.** اسکرول تنها نیست. انتخاب متن، کیبورد، باز کردن لینک یا جستجو باید همه جلوی حرکت رابط را بگیرند.
4. **نوبت جدید را نزدیک بالای ویوپورت شروع کنید.** تا نوبت جدید جایی برای خواندن از ابتدا داشته باشد.
5. **سپس جواب را استریم کنید.** جواب باید داخل صفحه رشد کند، نه اینکه فوری همه چیز را کنار بزند.
6. **بخشی از گفتگوی قبلی را در زمینه نگه دارید.** پرامپت و پاسخ باید بصری متصل بمانند و به‌اندازهٔ کافی از نوبت قبلی دیده شود تا خواننده بداند کجاست.
7. **بگذارید محتوای جدید خارج از صفحه برسد.** گفتگو می‌تواند بدون عوض کردن آنچه خواننده می‌بیند استریم کند.
8. **نشان دهید خارج از دید چه می‌گذرد.** وقتی پاسخ هنوز استریم می‌شود یا پیام‌های جدید رسیده‌اند واضح باشد.
9. **بازگشت به آخرین پاسخ را آسان کنید.** اقدام «پرش به جدیدترین» باید خواننده را برگرداند و دنبال‌کردن را از سر بگیرد.
10. **بگذارید افراد به هر جای گفتگو بپرند.** نخ‌های بلند به لینک پیام، جستجو، نشانگر نخوانده و ناوبری مستقیم نیاز دارند.
11. **جایی باز کنید که خواننده رها کرده.** گفتگوی ذخیره‌شده باید روی آخرین نوبت معنادار باز شود. اغلب آخرین پیام کاربر است، نه ته مطلق.
12. **وقتی چیدمان عوض می‌شود جای خواننده را حفظ کنید.** تصویر لود می‌شود. مارک‌داون باز می‌شود. بلوک کد رندر می‌شود. پیام‌های قدیمی‌تر بالا ظاهر می‌شوند. هیچ‌کدام نباید جای خواننده را بدزدند.
13. **وقفه را بدون دزدیدن موقعیت مدیریت کنید.** توقف، تلاش مجدد، بازتولید، شاخه یا خطا نباید ناگهان گفتگو را جابه‌جا کنند.
14. **در نخ‌های بلند پاسخگو بمانید.** متن استریم، مارک‌داون، کد، تصویر و تاریخچهٔ بلند باید همچنان روان حس شوند.
15. **بدون نویز دسترس‌پذیر باشید.** رونوشت را قابل‌ناوبری نگه دارید، فوکوس کیبورد را حفظ کنید و رویدادهای مهم را با ریتم راحت اعلام کنید.

**هرگز خواننده را خلاف نیتش حرکت ندهید.**

</DocsCollapsible>

`MessageScroller` یک اسکرولر رونوشت چت است که برای همین رفتارها ساخته شده.
`MessageScrollerProvider` مالک وضعیت اسکرول و رفتار ردیف رونوشت است:
موقعیت باز شدن، خروجی استریم، لنگر نوبت جدید، تاریخچهٔ پیش‌افزوده،
دیده‌شدن و کنترل‌های اسکرول. `MessageScroller` قاب استایل‌شده‌ای است که
داخل آن رندر می‌شود.

`MessageScroller` به ویوپورت اسکرول محدود است. مالک پیام‌ها، وضعیت AI،
حمل‌ونقل، پایداری، شاخه‌بندی یا وضعیت مدل نیست. کد محصول روی ترکیب پیام‌ها،
نشانگرها، ابزارها، پیوست‌ها و ورودی پرامپت متمرکز می‌ماند.

رفتار اسکرولی که چت نیاز دارد را می‌دهد، بدون اینکه بقیهٔ UI چت را بگیرد.
و حتی در گفتگوهای بلند با مارک‌داون غنی سریع می‌ماند.

```tsx
import { Message } from "@/components/ui/message"
import {
  MessageScroller,
  MessageScrollerButton,
  MessageScrollerContent,
  MessageScrollerItem,
  MessageScrollerProvider,
  MessageScrollerViewport,
} from "@/components/ui/message-scroller"
```

```tsx
<MessageScrollerProvider>
  <MessageScroller>
    <MessageScrollerViewport>
      <MessageScrollerContent>
        {messages.map((message) => (
          <MessageScrollerItem
            key={message.id}
            messageId={message.id}
            scrollAnchor={message.role === "user"}
          >
            <Message />
          </MessageScrollerItem>
        ))}
      </MessageScrollerContent>
    </MessageScrollerViewport>
    <MessageScrollerButton />
  </MessageScroller>
</MessageScrollerProvider>
```

`MessageScroller` والد خود را پر می‌کند؛ پس آن را داخل ظرفی با ارتفاع محدود بگذارید.

```tsx

  </MessageScrollerProvider>
</div>
```

## ترکیب

</div>

<DocsCollapsible title="ترکیب">

```tsx
<MessageScrollerProvider>
  <MessageScroller>
    <MessageScrollerViewport>
      <MessageScrollerContent>
        <MessageScrollerItem>
          {/* یک پیام، نشانگر یا ردیف */}
        </MessageScrollerItem>
        <MessageScrollerItem />
        <MessageScrollerItem />
      </MessageScrollerContent>
    </MessageScrollerViewport>
    <MessageScrollerButton />
  </MessageScroller>
</MessageScrollerProvider>
```

- **`MessageScrollerProvider`** — ریشهٔ بدون‌استایل. مالک وضعیت اسکرول و props رفتار برای موقعیت باز شدن، اسکرول خودکار، لنگر، فرمان‌های اسکرول و ردیابی دیده‌شدن.
- **`MessageScroller`** — قاب استایل‌شده. ویوپورت، محتوا و کنترل‌ها را داخل provider می‌چیند.
- **`MessageScrollerViewport`** — عنصر قابل‌اسکرول. رویدادهای اسکرول بومی را می‌گیرد و هنگام پیش‌افزودن پیام‌های قدیمی‌تر ردیف دیده‌شده را حفظ می‌کند.
- **`MessageScrollerContent`** — ظرف رونوشت. ردیف‌ها را نگه می‌دارد و پیش‌فرض‌های ناحیهٔ زنده برای پیام‌های جدید را فراهم می‌کند.
- **`MessageScrollerItem`** — مرز ردیف رونوشت. هر فرزند مستقیم محتوا را بپیچید تا اسکرولر بتواند اندازه بگیرد، لنگر کند، موقعیت را حفظ کند، دیده‌شدن را ردیابی کند و به آن بپرد. آیتم می‌تواند پیام، نشانگر، نشانگر تایپ، جداکننده، رویداد پیوستن/ترک یا ردیف «بارگذاری قبلی» باشد.
- **`MessageScrollerButton`** — کنترل اسکرول. به ابتدا یا انتهای رونوشت اسکرول می‌کند و تا وقتی در آن جهت محتوا نباشد inert است.

## لنگر نوبت‌ها

</div>

<DocsCollapsible title="لنگر نوبت‌ها">

نوبت بخشی از گفتگو است که تبادل جدید را شروع می‌کند. در چت سادهٔ AI معمولاً پیام کاربر و پاسخ دستیار بعدی است.

لنگر ردیفی است که ویوپورت باید آن را شروع آن نوبت بداند. آن ردیف را با `scrollAnchor` علامت بزنید. وقتی لنگر جدید اضافه می‌شود، ویوپورت آن را نزدیک بالا می‌برد و کمی از آیتم قبلی را بالای آن نگه می‌دارد تا نوبت جدید از زمینه‌اش جدا حس نشود.

```tsx
// به اسکرولر می‌گوید پیام کاربر را برای نوبت بعدی لنگر کند.
<MessageScrollerItem
  messageId={message.id}
  scrollAnchor={message.role === "user"}
/>
```

لنگرهای اسکرول به نقش پیام گره نخورده‌اند. هر ردیفی را می‌توانید لنگر کنید:
پیام کاربر، نشانگر سیستم، رویداد تحویل یا هر چیز دیگری که نوبت معنادار را شروع کند. `MessageScroller` فقط باید بداند کدام ردیف ویوپورت را لنگر کند.

در نمونهٔ زیر پیام کاربر لنگر است. وقتی پیام جدید می‌فرستید، ویوپورت آن را نزدیک بالا لنگر می‌کند و پاسخ دستیار را زیر آن اضافه می‌کند. لنگر را به پیام دستیار ببرید تا تفاوت را ببینید.

## حفظ زمینه در دید

</div>

<DocsCollapsible title="حفظ زمینه در دید">

وقتی نوبت جدید شروع می‌شود، باید همچنان بخشی از همان نخ پیوسته حس شود.
`scrollPreviousItemPeek` تکه‌ای از آیتم قبلی را بالای لنگر دیده‌پذیر نگه می‌دارد
تا خواننده زمینه را حفظ کند و حس نکند گفتگو روی صفحهٔ خالی از نو شروع شده.

```tsx
// ۶۴ پیکسل از نوبت قبلی را بالای ردیف تازه‌لنگرشده نگه دارید.
<MessageScrollerProvider scrollPreviousItemPeek={64}>
  <MessageScroller>{/* نوبت‌های لنگرشده */}</MessageScroller>
</MessageScrollerProvider>
```

مقدار peek را در نمونهٔ زیر تنظیم کنید تا اثرش روی گفتگو را ببینید.

## دنبال کردن لبهٔ زنده

</div>

<DocsCollapsible title="دنبال کردن لبهٔ زنده">

وقتی خواننده روی لبهٔ زنده است — چون مانده یا برگشته —
`autoScroll` پاسخ‌های استریم را هنگام رشد در دید نگه می‌دارد.
دور شدن از لبهٔ زنده — با چرخ، لمس، کلیدهای اسکرول کیبورد یا کشیدن نوار اسکرول —
دید را رها می‌کند. پرش صریح به پیام هم همین کار را می‌کند. سپس تکه‌های جدید
می‌توانند بدون جابه‌جایی خواننده برسند.

`autoScroll` با لنگر نوبت ترکیب می‌شود. وقتی نوبت جدید نزدیک بالا لنگر می‌شود،
دید ثابت می‌ماند در حالی که پاسخ در فضای زیر آن استریم می‌شود. وقتی پاسخ
ویوپورت را پر کرد، خواننده دوباره روی لبهٔ زنده است و دنبال‌کردن خروجی جای
لنگر را می‌گیرد.

```tsx
<MessageScrollerProvider autoScroll>
  <MessageScroller>{/* نوبت‌های استریم */}</MessageScroller>
</MessageScrollerProvider>
```

پیام `data-autoscrolling` می‌گیرند تا بتوانید در انتقال استایل شرطی بزنید.

## باز کردن نخ‌های ذخیره‌شده

</div>

<DocsCollapsible title="باز کردن نخ‌های ذخیره‌شده">

باز کردن نخ ذخیره‌شده در ته مطلق رونوشت معقول به نظر می‌رسد، اما اغلب
خواننده را بدون زمینهٔ کافی داخل گفتگو می‌اندازد. پیش‌فرض بهتر `"last-anchor"` است:
آخرین نوبت معنادار را نشان دهید — مثل آخرین پیام کاربر — با پاسخ زیر آن.

خواننده فوری جایی در نخ دارد. می‌بیند چه پرسیده، جواب از کجا شروع شده و بدون
بازسازی گفتگو از لبهٔ پایین ادامه می‌دهد.

```tsx
<MessageScrollerProvider defaultScrollPosition="last-anchor">
  <MessageScroller>{/* رونوشت */}</MessageScroller>
</MessageScrollerProvider>
```

`"last-anchor"` روی `scrollAnchor` کلید می‌خورد، نه نقش پیام. اگر لنگر نباشد،
یا آخرین نوبت لنگرشده از قبل در ویوپورت جا شود، به `"end"` برمی‌گردد.

وقتی می‌خواهید از ابتدای گفتگو ادامه دهید از `"start"` استفاده کنید، یا وقتی
آخرین پیام مطلق جای درست فرود است از `"end"`.

## جلوگیری از فلش هنگام بارگذاری مجدد

</div>

<DocsCollapsible title="جلوگیری از فلش هنگام بارگذاری مجدد">

ظرف اسکرول همیشه از بالا باز می‌شود. HTML راهی برای تنظیم `scrollTop` ندارد،
پس رونوشت سرور-رندرشده اول قدیمی‌ترین پیام‌ها را نشان می‌دهد. بعد از اجرای
جاوااسکریپت، `defaultScrollPosition` دید را جابه‌جا می‌کند و پرش می‌بینید.

وقتی `defaultScrollPosition` برابر `"end"` یا `"last-anchor"` است، ویوپورت تا
اعمال آن موقعیت `data-pending-scroll` دارد. ویوپورت استایل‌شده تا حضور آن
ویژگی پنهان می‌ماند تا قاب را ببینید نه پرش را. `"start"` به این نیاز ندارد.

اگر می‌خواهید `"end"` در اولین paint دیده شود، بلافاصله بعد از ویوپورت یک اسکریپت
inline بگذارید. به ویوپورت `id` بدهید، به پایین اسکرول کنید و `data-pending-scroll`
را بردارید.

```tsx
const scrollToEndScript = `(function () {
  var viewport = document.getElementById("messages")
  if (!viewport) {
    return
  }
  viewport.scrollTop = viewport.scrollHeight
  viewport.removeAttribute("data-pending-scroll")
})()`

<MessageScroller>
  <MessageScrollerViewport id="messages" suppressHydrationWarning>
    <MessageScrollerContent>{/* رونوشت */}</MessageScrollerContent>
  </MessageScrollerViewport>
  <script dangerouslySetInnerHTML={{ __html: scrollToEndScript }} />
  <MessageScrollerButton />
</MessageScroller>
```

اسکریپت را در صفحه بگذارید، نه داخل اسکرولر. فقط برای `"end"` کار می‌کند و
فقط وقتی پیام‌ها از قبل در HTML هستند. روی ویوپورت `suppressHydrationWarning`
بگذارید. اگر CSP دارید، `nonce` بدهید.

این اسکریپت را با `"last-anchor"` استفاده نکنید. وقتی پیام‌ها سمت کلاینت لود
می‌شوند آن را رد کنید.

</DocsCollapsible>

## پویانمایی پیام‌های جدید

</div>

<DocsCollapsible title="پویانمایی پیام‌های جدید">

`MessageScrollerItem` را می‌توان مستقیم پویانمایی کرد. نسخهٔ motion از آیتم

حس بالا آمدن از لبهٔ زندهٔ ویوپورت بدهد.

```tsx
const MotionMessageScrollerItem = motion.create(MessageScrollerItem)
```

## پرش به پیام‌ها

</div>

<DocsCollapsible title="پرش به پیام‌ها">

نتایج جستجو، permalinkها، آیتم‌های طرح کلی و دکمه‌های نوار ابزار اغلب باید
رونوشت را از بیرون لیست پیام هدایت کنند. برای آن کنترل‌ها از `useMessageScroller`
استفاده کنید. چون هوک‌ها از `MessageScrollerProvider` می‌خوانند، در هر کامپوننت
داخل provider کار می‌کنند — از جمله کنترل‌هایی که بیرون قاب `MessageScroller`
رندر می‌شوند.

```tsx
import { useMessageScroller } from "@/components/ui/message-scroller"
```

```tsx
const { scrollToMessage, scrollToEnd, scrollToStart } = useMessageScroller()
```

`scrollToMessage` به `messageId` روی `MessageScrollerItem` هدف می‌زند؛ پس
ردیف‌هایی که باید آدرس‌پذیر باشند باید id پایدار داشته باشند. وقتی هدف mount
نیست و صف‌بندی ممکن نیست، `scrollToMessage` مقدار `false` برمی‌گرداند.

`scrollToMessage` می‌تواند قبل از وجود آیتم‌ها هدف را صف کند — برای permalinkهای
حل‌شده سمت کلاینت هنگام mount رونوشت. بعد از mount ردیف‌ها، id گم‌شده به‌جای
شروع حلقهٔ حدس‌زنی `false` برمی‌گرداند. نتیجهٔ `true` یعنی اسکرول اجرا یا صف
شده، نه اینکه ردیف از قبل در دید باشد.

## کارایی

</div>

<DocsCollapsible title="کارایی">

`MessageScroller` در برابر رونوشت‌های بزرگ با مارک‌داون و ردیف‌های پیام ترکیبی
بنچمارک شده است.

هدف کارایی ما برای `MessageScroller` نگه داشتن مسیر داغ اسکرول بیرون از وضعیت
React است: بدون رندر مجدد React برای ردیف‌های رونوشت، بدون layout اجباری در هر
اسکرول، و تا جایی که مرورگر بتواند کار paint خارج از صفحه را کم کند.

موقعیت اسکرول، لنگر و دنبال‌کردن خروجی به‌صورت imperatively ردیابی و از طریق
ویژگی‌های `data-*` روی ریشه و ویوپورت آینه می‌شوند؛ پس اسکرول و استریم ردیف‌های
رونوشت را دوباره رندر نمی‌کنند.

`MessageScrollerItem` استایل‌شده همچنین با `content-visibility: auto` و
`contain-intrinsic-size` عرضه می‌شود. ردیف‌ها برای انتخاب، کپی، find-in-page،
SSR و فناوری کمکی در DOM می‌مانند، اما مرورگر می‌تواند کار رندر ردیف‌های دور از
ویوپورت را رد کند.

ردیابی دیده‌شدن pay-for-what-you-use است. منوی پرش یا نشانگر نوبت فعال تا وقتی
چیزی به `useMessageScrollerVisibility` مشترک نشود هزینه‌ای ندارد.

این برای بازهٔ مورد انتظار رونوشت چت راحت است: صدها تا هزاران کم نوبت، شامل
پیام‌هایی با مارک‌داون و کامپوننت‌های ترکیبی.

</DocsCollapsible>

## مجازی‌سازی

</div>

<DocsCollapsible title="مجازی‌سازی">

مجازی‌سازی عمداً بیرون از primitive مانده است. `MessageScroller`
ردیف‌های DOM واقعی رندر می‌کند و تا هزاران نوبت سریع می‌ماند (ببینید
[کارایی](#کارایی))؛ پس بیشتر رونوشت‌ها هرگز به آن نیاز ندارند.

وقتی رونوشت آن‌قدر بزرگ است که مجازی‌سازی لازم است، `MessageScrollerViewport`
را به‌عنوان عنصر اسکرول بگیرید و بگذارید مجازی‌ساز مالک ردیف‌ها باشد.

```tsx showLineNumbers
import * as React from "react"
import { useVirtualizer } from "@tanstack/react-virtual"

function VirtualizedTranscript({
  messages,
}: {
  messages: Array<{ id: string; content: React.ReactNode }>
}) {
  const viewportRef = React.useRef<HTMLDivElement>(null)

  const virtualizer = useVirtualizer({
    count: messages.length,
    getScrollElement: () => viewportRef.current,
    estimateSize: () => 86,
    getItemKey: (index) => messages[index]?.id ?? index,
    overscan: 8,
  })

  return (
    <MessageScrollerProvider>
      <MessageScroller>
        <MessageScrollerViewport ref={viewportRef}>
          <MessageScrollerContent className="block min-h-full">
            <div
              className="relative w-full"
              style={{ height: virtualizer.getTotalSize() }}
            >
              {virtualizer.getVirtualItems().map((virtualItem) => {
                const message = messages[virtualItem.index]

                if (!message) {
                  return null
                }

                return (
                  <div
                    key={virtualItem.key}
                    ref={virtualizer.measureElement}
                    data-index={virtualItem.index}
                    className="absolute start-0 top-0 w-full"
                    style={{
                      transform: `translateY(${virtualItem.start}px)`,
                    }}
                  >
                    <Message>{message.content}</Message>
                  </div>
                )
              })}
            </div>
          </MessageScrollerContent>
        </MessageScrollerViewport>
        <MessageScrollerButton />
      </MessageScroller>
    </MessageScrollerProvider>
  )
}
```

</DocsCollapsible>

## دسترس‌پذیری

</div>

<DocsCollapsible title="دسترس‌پذیری">

`MessageScroller` ظرف اسکرول را با کیبورد در دسترس نگه می‌دارد و رونوشت را
قابل‌اعلام می‌کند بدون اینکه UI پیام خاصی را تحمیل کند.

`MessageScrollerViewport` به‌صورت پیش‌فرض ناحیهٔ اسکرول برچسب‌دار و قابل‌فوکوس
با کیبورد است. از `role="region"`، `aria-label="Messages"` و `tabIndex={0}`
استفاده می‌کند تا کاربران کیبورد بتوانند رونوشت را فوکوس و مستقیم اسکرول کنند.

`MessageScrollerContent` رونوشت را با `role="log"` و `aria-relevant="additions"`
به‌عنوان ناحیهٔ زنده علامت می‌زند. ردیف‌های جدید می‌توانند اعلام شوند، اما
تغییرات متن استریم لازم نیست توکن‌به‌توکن اعلام شوند.

```tsx
<MessageScrollerContent aria-busy={status === "streaming"}>
  {/* پیام‌ها */}
</MessageScrollerContent>
```

اگر اعلام‌ها باید منتظر ردیف پیام کامل بمانند، هنگام استریم نوبت `aria-busy`
بدهید.

`MessageScrollerButton` یک دکمهٔ واقعی رندر می‌کند. وقتی چیزی برای اسکرول به آن
سمت نیست، `inert` می‌گذارد، `tabIndex={-1}` می‌گیرد و `data-active="false"`
می‌گذارد تا کنترل‌های اسکرول غیرفعال توقف فوکوس اضافه نسازند.

</DocsCollapsible>
